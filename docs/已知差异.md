# 已知差异（预览 vs 导出）

> **隐瞒差异比差异本身更严重。** 这份清单是"我们没有做到像素级一致"的正式声明。
> 结论先说：**元素框的几何是一致的（误差 0px）**；**文本的行盒与断行位置存在差异**，且其中一部分在当前技术路线下无法消除。

## 0. 一句话结论

| 层面 | 一致性 | 依据 |
|---|---|---|
| 画布尺寸 | ✅ 完全一致 | 1280×720 px ≡ 12192000×6858000 EMU，实测无误差 |
| 元素框 x/y/w/h | ✅ 一致（≤2px 达标，实测 0px） | `tests/geometry.test.ts` 逐元素比对 |
| 字号 | ✅ 一致 | px → pt 严格 ×0.75 |
| 颜色 | ✅ 一致 | 十六进制原样写入 |
| **文本行盒 / 断行位置** | ⚠️ **可能不同** | 见 D1、D2 |
| **避头尾（标点不上行首）** | ⚠️ **导出侧无法保证** | 见 D3 |
| **图表外观** | ⚠️ **不同** | 见 D4 |
| **字体** | ⚠️ **依赖目标机器** | 见 D5 |

---

## D1 · 文本行盒：我们控制了行数，但控制不了字形度量

**现状**：折行由 IR 层预折行决定，所以"共几行、每行是什么字"两个渲染器一致。
**差异**：每一行内部，文字在行盒里的垂直位置与基线由渲染器自己的字体度量决定。

- DOM：`line-height` 精确等于 `lineHeightPx`，文字垂直居中于行盒；
- PowerPoint / WPS：`lineSpacing` 是"行距"，实际行高 = 字体 ascent+descent+行距，与 CSS 的行盒模型不同；
- 结果：**多行文本块的第 2 行起可能出现 1–4px 的累积偏移**（取决于字号与字体）。

**影响范围**：多行正文、要点列表。单行标题影响可忽略。
**为什么不修**：要修必须拿到目标字体的真实度量（ascent/descent/leading）并改写行距算法，而 WPS 与 PowerPoint 对同一字体的度量也可能不同。这属于"投入产出比不成立"，故如实记录。

## D2 · 中文避头尾（kinsoku）只能近似

**现状**：`wrapText()` 做了保守近似 —— 行首禁则标点会被拉回上一行，行尾开括号会被推下去。
**差异**：
- 浏览器有原生 kinsoku，可能与我们的切分不同（我们优先保证"标点不落行首"，宁可轻微超宽）；
- **pptx 侧没有任何可控属性**：PptxGenJS 未暴露避头尾开关，PowerPoint 用自己的一套规则；
- 结果：导出后**行首仍可能出现 `，` `。`**，尤其是我们主动把标点拉回上一行导致该行超宽、而 PowerPoint 选择自己断行时。

**影响范围**：正文、要点。标题（短、通常一行）基本不受影响。
**缓解**：内容层限制单条要点字数（≤40 字），减少标点落在边界的机会。

## D3 · 自动缩放：我们**不用**渲染器的自动缩放

**决策**：导出时**不传 `fit`**。实测依据：PptxGenJS 不传 `fit` 时**不写任何 autofit 节点**，PowerPoint 与 WPS 都不会替我们缩放文本；而 `fit:'shrink'` 的 `fontScale` 不可控（上游 #1199），会让预览与导出必然不一致。

**代价（必须知道）**：如果估算器算错了，文字会**可见地溢出**，而不是被渲染器悄悄缩小。
**这是有意的取舍** —— 可见溢出可测、可修；偷偷缩小不可测。

## D4 · 图表外观

**现状**：导出用**原生 pptx 图表**（`c:barChart` 等），数据可编辑（右键"编辑数据"）。
**差异**：
- 预览是我们自己画的 SVG/canvas（简版），导出是 PowerPoint 原生图表 → **坐标轴刻度、网格线、图例位置、间距全部不同**；
- 颜色通过 `chartColors` 传入，基本一致，但原生图表会自行调整配色对比度；
- 我们只在预览里画了"简化坐标轴"，PowerPoint 会画出完整刻度与数值标签。

**影响范围**：所有数据页。
**定位**：预览是"版式结构预览"，不是"图表渲染预览"。**不承诺图表外观一致。**

## D5 · 字体：只存名字，不嵌字体

**现状**：pptx 只记录字体名（实测确认：包内无 `.fntdata`），目标机器没装该字体时会被替换。
**差异**：字体被替换 → 字宽变化 → 我们预折行的行可能变宽 → 溢出。

**缓解（已实现）**：
1. 字体白名单只有 4 个中文字体（微软雅黑 / 等线 / 思源黑体 / 宋体）；
2. `/settings` 有**字体缺失检测**，逐项显示"本机有没有"；
3. 内容层有字数预算，留了安全余量（单行宽度系数 `sans ×1.18`）。

**残余风险**：完全无法根治。这是 pptx 格式本身的限制。

## D6 · 主题只部分映射到 pptx 母版

我们的 Theme 有 11 个颜色 token + 间距节奏 + 圆角 + 描边，而 pptx 的 theme 只有 `clrScheme` + `fontScheme`。
因此：**颜色与字体映射进母版；间距/圆角/描边是逐元素写入的**，不会出现在 PowerPoint 的"主题颜色"面板里。

用户如果在 PowerPoint 里点"设计 → 变体"换配色，**我们的间距与圆角不会跟着变**。

## D7 · 段落间距与项目符号

- 预览的项目符号是**我们自己画的小圆点**（为了几何可控），导出也是画的椭圆形状 —— 两边一致；
- 但它不是 PowerPoint 的"列表样式"，用户在 pptx 里按 Tab 缩进不会自动变成二级列表；
- 预览里要点之间的间距由 `BULLET_GAP=10px` 固定，导出相同；然而 PowerPoint 的"段落间距"若被用户手动改动，会与我们不一致。

## D8 · 图片

本期**不接图库、不抓商业素材**（红线），`image` 槽位默认是**纯图形占位块**（虚线边框 + 说明文字）。
- 预览：`div` 虚线框；
- 导出：`rect` + `dashType: dash` 边框。
两者外观接近但边框样式细节不同（虚线段长度由渲染器决定）。

## D9 · 逐页 PNG 与预览的关系

PNG 由 `raster.ts` 按 `ResolvedSlide` 重绘（不是截图 DOM），所以：
- 几何、颜色、文本位置与预览一致；
- 但 PNG 用 canvas 的字体渲染，与浏览器 DOM 的抗锯齿/字重略有差异；
- 图表同样是我们自己画的简版（同 D4）。
