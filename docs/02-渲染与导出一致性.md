# 02 · 渲染与导出一致性

> 本文件说明"预览"和"导出"为什么能对齐、对齐到什么程度、以及哪些地方**做不到**（后者见 `docs/已知差异.md`，不重复）。

## 1. 单一事实源：不是口号，是三条硬约束

```
                ┌──────────────────────┐
                │   Slide IR (JSON)    │  ← 唯一事实源，zod 校验
                └──────────┬───────────┘
                           │ resolveSlide()
                           ▼
                ┌──────────────────────┐
                │  ResolvedSlide[]     │  ← 坐标/字号/折行 在这里定死
                └────┬────────────┬────┘
                     │            │
         ┌───────────▼──┐    ┌────▼─────────────┐
         │ DOM 渲染器    │    │ Pptx 渲染器      │
         │ (预览)        │    │ (导出, EMU)      │
         └──────────────┘    └──────────────────┘
```

1. **两个渲染器都只消费 `ResolvedSlide`**，谁都不许自己再算一遍坐标或字号；
2. **折行在 `resolve` 阶段就定死**（预折行），两个渲染器拿到的是同一串行文本；
3. **项目符号条目的几何只有一个来源**：`bulletItemBoxes()`，DOM / pptx / PNG 三个渲染器 + 几何测试共用（这条是踩出来的——三处各算一遍必然漂移）。

## 2. 预折行：一致性最关键的一个设计

pptx 里如果给一个文本框 + 一段长文本，PowerPoint 会按**它自己的**字体度量换行；浏览器按**它自己的**换行。两套度量必然不同，于是：
- 预览显示 3 行，导出变成 4 行 → 溢出；
- 想靠 `fit:'shrink'` 兜底，缩多少由查看器决定 → 预览与导出必然不一致。

所以我们反过来做：**在 IR 层把文本切成行，两个渲染器都按行渲染**。

| 渲染器 | 做法 |
|---|---|
| DOM | 每行一个固定行高的 `div`（`white-space: pre`，不接受浏览器再换行） |
| Pptx | 每行一个段落，`wrap: false`，行距按 `lineHeightPx × 0.75` 换算成 pt |
| PNG | 逐行 `fillText`，行高同上 |

代价：中文避头尾只能做近似（见已知差异）；收益：**行数与行位置一致**。

## 3. 单位换算：唯一常量来源

`src/lib/ir/constants.ts`：

```
1 inch  = 914400 EMU
96 px   = 1 inch            (画布 1280×720 @96dpi)
1 px    = 9525 EMU
1280 px = 12192000 EMU ； 720 px = 6858000 EMU
px → pt = × 0.75
```

**禁止在任何地方写死 1280 / 720 / 9525 / 13.333。** 实测验证：`pptxgenjs` 写出的 `sldSz` 正是 `12192000 × 6858000`，读回 `x=80px` 精确还原为 `80.000px`（误差 0）。

### 4.1 包结构体检的 12 项断言

针对四类真实缺陷，全部可在 CI 跑：

| 断言 | 防的是什么 |
|---|---|
| `[Content_Types].xml` 存在且可解析 | 缺了直接"需要修复" |
| 每个 `Override` 指向真实部件 | **幽灵 slideMaster**（PptxGenJS #1444，4.0.1 实测复现 5 个） |
| 每个 `.rels` 的 Target 可解析 | 断链（OfficeCLI #602 漏判的正是这类） |
| 每个部件都有 Content-Type | 否则 PowerPoint 拒绝 |
| XML 1.0 非法控制字符扫描 | 备注/正文含 `0x00-0x08` 等 → "需要修复" |
| `sldSz == 12192000×6858000` | 画布口径漂移 |
| **图表轴引用完整性** | **孤儿 `<c:axId>`（PptxGenJS #1534，4.0.1 三个图表全中）** |
| **`dLblPos` 与图型匹配** | #1546（bar 专属取值串进 line） |
| **notesMaster 占位符 ≥5** | #1443（plus 4.3.6 回归成 0 个） |
| 备注部件存在且含中文 | 备注丢失 |
| 至少 1 页 | 空文件 |
| 无 `.fntdata` | 确认"只存字体名"这个前提成立 |

### 4.2 几何一致性测试怎么算

```ts
// tests/geometry.test.ts
1. 8 个版式 → resolve → 得到每个元素的 IR 坐标（px）
2. 渲染成 pptx → 后处理 → 解压 → 从每页 XML 抽 <a:off>/<a:ext>（EMU→px）
3. 每个元素都必须找到一个坐标差 ≤ 2px 的落点；宽度差同样 ≤ 2px
```

实测结果：**全部命中，误差 0px**（因为 1px 严格等于 9525 EMU，换算无损）。断言数量随版式/元素增加而增加。

## 5. 后处理层（必需，不是优化）

导出后统一走 `postProcessPptx()`：

| 动作 | 为什么必需 | 实测 |
|---|---|---|
| 换回合规 `notesMaster` | pptxgenjs-plus 4.3.6 写成空骨架（1113 B / 0 占位符） | 替换为 7504 B / 6 占位符 |
| 清理非法控制字符 | 备注里一个 `\u0001` 就够触发修复 | 已纳入断言 |
| 重打包压缩 | 两版 pptxgenjs 都 100% STORE，一个字节没压 | **166 KB → 50 KB（−70%）** |

**这条策略经过验证**：`4.0.1` 的产物 4 项失败 → `plus` 1 项失败 → **plus + 后处理 = 18/18 全通过**（含读回）。详见 `docs/research/F-导出spike2-版本A-B实测.md`。
