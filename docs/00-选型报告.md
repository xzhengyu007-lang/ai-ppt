## 2. 三个必须回答的结论

### 2.1 pptx 生成到底用谁

**结论：用 "PptxGenJS 引擎" 的活跃分支，把库关进一个文件，并预留自研出口。**

**为什么不是"换一个库"**：约束是"浏览器里直接生成**可编辑** pptx"。这条约束把候选池砍到只剩 PptxGenJS 家族 —— python-pptx / officegen / POI / Open-XML-SDK 全是服务端，装了它们就要背 Python/JVM 服务 + 容器 + 中文字体环境，与"静态前端一键导出"正面冲突。

**三级方案（这是本报告最重要的表）**：

| 级别 | 方案 | 触发条件 | 成本 |
|---|---|---|---|
| **G0 默认（已 A/B 实测确认）** | `lofcz/pptxgenjs-plus@4.3.6`（MIT，**19★**）**vendor 进仓库**，只在 `src/renderer/pptx/adapter.ts` 一个文件 import，**并叠一层出口后处理补 notesMaster** | — | 后处理 ~1 个自写模块 |
| **G1 降级** | `gitbrent/PptxGenJS@4.0.1`（同 API，**本会话已实测可生成中文+备注+原生柱图**）+ 把必需修复打成 `patches/` | plus 停更 >6 个月 / 不兼容 / 关键 bug 不回 | 改 1 个 import + 1 个 patch |
| **G2 换实现** | 自研 OOXML 渲染器（路线图：`ppt-master` 的 `pptx_ooxml/` MIT，或 `genoffice` 的 `pptx-engine` Apache-2.0） | 4.x 线整体不可用（大面积"需要修复"绕不过） | 中（**只换一个渲染器，IR 与业务零改动**） |

**A/B 已经做完了（`docs/research/F-导出spike2-版本A-B实测.md`），结论是 plus 胜出且差距很大**：同一份 6 页输入分别喂给两版，`4.0.1` 的**三个图表全部**引用 3 个轴却只定义 2 个（孤儿 `2094734556`，与 #1534 标题逐字吻合），另有 5 个幽灵 slideMaster（#1444）；`plus 4.3.6` 这两项全清。但 plus 自己**回归了 notesMaster**（空骨架、0 个占位符），必须由后处理补回——补回后**14/14 全 PASS**。

所以默认版本不再是"凭直觉选"，而是实测选的；同时这条也证明了一件事：**没有任何单一版本可以开箱即用，出口后处理层是必需品而不是可选项**。

**两条独立旁证，说明这个引擎能撑住**：
1. 我自己的 spike：`pptxgenjs@4.0.1` 生成 16:9 中文 deck，包结构断言 **23/23 PASS**（详见 §2.3）。
2. 9,472★ 的 PPTist 生产代码里导出 pptx **就是纯前端 `pptxgenjs` + `file-saver`**，无后端、无 LibreOffice（`gh search code` 命中 0 个 LibreOffice 引用）。

**同时必须记住天花板在哪**：两个最认真的原生 pptx 项目 —— `ppt-master`（74,872★）和 `genoffice`（11,958★）—— 都**自己写 OOXML 引擎**；genoffice 甚至把 `pptxgenjs@^4.0.1` 只留作 devDependency 做对比测试。这不是巧合：**保真度要求继续上升时，自研 OOXML 是必然终点**。好消息是双渲染器架构让这次迁移只影响一个渲染器。

### 2.2 预览怎么做

**结论：DOM 渲染 Slide IR，等比缩放；不引入任何画布引擎、不引入 tldraw/konva/fabric/dnd-kit。**

- 三层 DOM：外层容器 → `transform: scale(s)` 的 wrapper → 内部 1280×720 真实尺寸层。**手柄与辅助线必须放在 scale 层外侧**，否则 1px 边在 50% 缩放下消失、200% 下变粗。
- 拖拽换算只用一行：**`delta ÷ scale`**，不要走 `getBoundingClientRect` 反算（这是 90% 坐标偏移坑的根因）。
- 用 `ResizeObserver` 盯中栏容器，**不要盯 window**（左右栏可拖拽，中栏变宽不会触发 window resize）。
- 撤销/重做用**快照式**（IR 很小，`structuredClone` 十几页毫无压力），不用命令式 —— 换版式/换主题/页序这类结构性操作写逆操作必错。
- **新增运行时依赖 0 个**。可选 `zundo`（0.6KB gzip, MIT）替代手写快照栈。
- 明确不用 `dnd-kit`：它有一整族 issue（#1290/#1852/#2041）是 `transform: scale()` 容器内系统性错位，#2041 至今 OPEN。

### 2.3 要不要 LibreOffice

**结论：不要。**

1. **本机就没有**：`soffice` 不在 PATH，两个默认安装路径都不存在；`docker` 也不在 PATH。装它等于给交付加一个重依赖，而本机验收并不需要它。
2. **本机有真 PowerPoint(Office16) + 真 WPS**：任务书要的"两台真机各开一次、截图存 `docs/evidence/`"在本机就能完成，比"LibreOffice 转 PDF 间接证明"更权威。
3. **6 个 AI-PPT 候选里只有 2 个强依赖 LibreOffice，且恰好是部署最重的两个**（LandPPT 的 `libreoffice-impress` sidecar + PPTAgent 要求 PATH 有 `libreoffice`；前者还叠加 Apryse 付费锁与邀请码）。主流 4/6 都是纯代码写 OOXML。
4. LibreOffice 自身还会引入新坑：它忽略 `wrap="none"`（单行框仍按框宽换行，末尾字掉行，`ppt-master` #199）。
5. **替代校验链（已实测跑通闭环）**：
   - 包结构体检（自写 8 项断言，`zipfile`+`xml.etree`，JS 版已实测 22 个 XML 部件 0 处非法字符）
   - python-pptx 读回（已实测 **9/9 PASS**，几何 `x=80px` 精确还原为 `x=80.000px`）
   - 真机 PowerPoint + WPS 人工截图（Phase 2 交付证据）
   - CI 可选 job 跑 LibreOffice —— **非阻塞**，没有就不跑。

### 3.2 一条需要现在拍板的技术细节：`fit` 怎么处理

任务书已知陷阱写着"`fit:shrink` 不可靠，PowerPoint 与 WPS 表现不同 → 自己在 IR 层按预算截断/降字号，不依赖渲染器"。调研把这句话落成了具体事实：

- **PptxGenJS 默认不写任何 autofit 节点** —— 我在 spike 里实测确认（`normAutofit`/`spAutoFit`/`noAutofit` 三者皆无）。也就是说：**不设 `fit` 时，两个渲染器都不会自动缩放**，文字会不会溢出完全由我们的估算器决定。
- PPTist 的写法是 `if (!el.fixedHeight) options.fit = 'resize'`，而 `resize` → `<a:spAutoFit/>` 是"**框长高**、字不缩"，槽位制下会让框静默撑破版心。
- `fit:'shrink'` → `<a:normAutofit/>` 的 `fontScale` 不可控（PptxGenJS #1199 挂了近 4 年），意味着缩多少由查看器决定 → **预览与导出必然不一致**。
- 而 `normAutofit` 在 WPS 是否生效，本会话**无可引 issue**（`gh search issues` 在本环境报 Invalid search query，已如实标未核实）。

**所以决策是：不传 `fit`，不回退到任何渲染器自动缩放，溢出完全由 IR 层确定性估算器负责。**
这样 PowerPoint、WPS、网页预览三者看到的是同一份几何，跨渲染器一致性最好。代价是：估算器算错时文字会**可见地溢出**（而不是被偷偷缩小）——这正是我们要的，因为可测、可修。

### 6.1 本次调研过程中我自己犯并纠正的错误（一并记录，避免后面重踩）

1. **误判 `pushed_at`**：PptxGenJS 的 `pushed_at=2025-11-28` 看似在 6 个月内，实际是**非主分支**（`issue-1396` WIP）推送，master 停在 2025-06-26。→ **一律以 default branch 最新 commit 为准。**
2. **spike 校验器自己的 bug**：`<a:off>` 正则先命中了 spTree 组级 `x="0" y="0"`，误报 2 条 FAIL。修正断言后 23/23 PASS —— **失败时先怀疑自己的断言**。
3. **PowerPoint COM 自动化不可用**：`New-Object -ComObject PowerPoint.Application` 首调抛 `RPC_E_CALL_REJECTED(0x80010001)`，加重试后卡在模态框，留了两个僵尸 `POWERPNT` 进程（已清理）。→ **真机验收改为人工截图，不做 COM 自动化。**
4. **`.ps1` 中文注释导致解析失败**：Windows PowerShell 5.1 把无 BOM 的 UTF-8 `.ps1` 当 ANSI 解码，报 `Unexpected token '}'` 且行号错位。→ **`.ps1` 带中文必须存 UTF-8 with BOM**；D 线独立踩到同一个坑。
5. **`powershell -File script.ps1 a b c` 只绑定第一个位置参数**（`param([string[]]$Repos)` 未加 `ValueFromRemainingArguments`），导致一次只查了一个仓库而不报错。→ **多参数必须加 `ValueFromRemainingArguments`，且核对输出条数。**
6. **npm/pip 缓存目录在 workspace 外会被沙箱拒绝写**（`EPERM` / `Errno 13`）。→ npm 加 `--cache .research/npm-cache`；pip 改用"直接下载 wheel 解压"（这也正好验证了离线安装路径）。
